# Kasa

**Status:** S2 Shaped · active · last reviewed 2026-10-02

A shelf of small browser games. The shelf lists what is on it and links to
each game; a game is a page of its own, in its own folder, with its own
version. Nothing is shared between them and nothing is imposed on them, so a
new idea is a new folder and a broken game cannot take the shelf down with it.

**Binding constraint:** one person, `$0`, no artist. Node and TypeScript only,
no runtime dependency, everything drawn and synthesised in code. A game that
needs a framework or an asset pipeline does not belong here.

## Running it

```bash
npm install
npm run play      # build the shelf and every game, then serve on :5190
```

| | |
|---|---|
| `npm run manifest` | rebuild `games.json` from each game's `game.json` |
| `npm run build:shell` | compile the shelf |
| `npm run build:games` | compile every game, each with its own tsconfig |
| `npm run typecheck` | check the shelf and every game at once |

## Adding a game

```bash
mkdir -p games/<id>/src
```

Then four things, all inside that folder:

| | |
|---|---|
| `game.json` | `id` (same as the folder), `version`, `title`, `blurb`, `accent`, `year` |
| `index.html` | the game's own page; load `./dist/<entry>.js` as a module |
| `tsconfig.json` | `{ "extends": "../../tsconfig.base.json", … }` — copy Tazaung's |
| `src/` | the game |

`npm run build` picks it up. **There is no list to edit** — the manifest is
generated by scanning `games/*/game.json`, so the only place that knows about
a game is the game's own folder. Drop a `poster.svg` beside `game.json` and
the card uses it; without one the card shows the title on the game's `accent`.

## Why there is no engine

The obvious move is a shared runtime — a `Game` interface, a loop, a scene
graph — and it is the wrong one with a single game to go on. Canon 09 puts
"new abstractions before the second real use case exists" under what does not
help, and this is exactly that case: the next game may be a DOM puzzle with no
canvas and no loop at all, and a framework shaped around Tazaung would be in
its way.

So the shelf and the games share **nothing**: no API, no base class, no
runtime, not even a router. A game is reached at its own URL, as its own
document. Whatever turns out to be genuinely common can be lifted out once a
third game has shown what that is.

The one thing not left to each game is TypeScript itself: there is a single
`package.json` at the root, so one `npm install` covers everything and there
is no copy of the compiler per game. Versions live in `game.json`, not in a
`package.json`, so they stay independent of npm. A game that one day needs its
own dependency gets its own `package.json` then, and not before.

## Layout

```text
index.html             the shelf
games.json             generated — not committed
src/shell/             reads games.json, renders cards; knows nothing else
games/<id>/            one game, standing alone
  game.json            the only place that describes it
  index.html           its own page
  tsconfig.json        its own build
  src/                 its own code
tools/manifest.ts      games/*/game.json → games.json
tools/build-games.ts   tsc per game
tools/serve.ts         dev static server, serves folder indexes
```

## Stage notes

S2 per [canon 02](../SPO/02-PROJECT-LIFECYCLE.md): git from the start. A single
game could have stayed an S0 sketch, but this repository is what holds every
game, so losing it loses more than one thing.

Still missing for S2: `lint`, `format` and `test` scripts, and CI. `typecheck`
is the only check wired up. `tools/` is outside `include`, so the build
scripts are not typechecked until `@types/node` arrives.

Two deliberate deviations from `SPO/tsconfig.base.json`, both because this runs
in a browser rather than Node: `lib` includes `DOM`, and `types` is empty
instead of `["node"]`. Not Archetype B either: a monorepo buys independent
versioning and publishing, and this needs neither — see
`ARCHITECTURE.md`.
